# 報酬設計ドキュメント

## プロジェクト概要

### 目的
2Dシミュレーター環境でミニカーの自動運転をPPO強化学習で実現し、実機（TT-02シャーシ）への転移（Sim2Real）を目指す。

### 最終目標
**6分間の連続周回レースで、壁にぶつからず、なるべく早く、チェックポイントを順番に通過してゴールに到達すること。**

---

## タスク定義

### 求める行動
1. **壁にぶつからない** - 衝突なしで走行
2. **なるべく早く** - 最短時間でゴール
3. **正しいルートを走る** - チェックポイントを順番に通過
4. **ゴールに到達する** - 全チェックポイント通過後にゴールエリアへ

### 環境仕様
- **観測空間（10次元）:**
  - LiDAR: 5方向（前方120度: -60°, -30°, 0°, +30°, +60°）
  - 速度: vx, vy（2次元）
  - 角速度: 1次元
  - 前回の行動: steering, throttle（2次元）

- **行動空間（2次元連続）:**
  - steering: [-1.0, 1.0]（左/右）
  - throttle: [-1.0, 1.0]（後退/前進）

- **物理パラメータ:**
  - max_steps: 2000（1エピソードの最大ステップ数）
  - 車両: TT-02実機スペック（全長479mm、全幅188mm、ホイールベース257mm）
  - タイムステップ: 1/60秒

### 成功条件
- **Success（ゴール到達）:** 全チェックポイントを順番に通過し、ゴールエリアに到達
- **Failure（失敗）:** 壁に衝突、またはmax_steps到達

---

## 報酬設計の原則

### 設計方針
1. **シンプルであること** - 必要最小限の項目でタスクの本質を捉える
2. **矛盾がないこと** - 各項目が互いに矛盾しない
3. **Sim2Real対応** - 実機で再現可能な報酬設計（報酬関数は学習時のみ使用）

### 報酬ハッキングの防止
- 生存報酬と時間ペナルティの矛盾を避ける
- 不要な項目を追加しない
- 各項目の係数バランスを慎重に設定

## 現在の報酬設計（v3.2）

### 報酬関数の構成

```python
def _compute_reward(self) -> float:
    reward = 0.0

    # 1. 時間ペナルティ
    reward -= 0.7  # v3.2: -1.0 → -0.7

    # 2. チェックポイント方向報酬
    if self.next_checkpoint_index < len(checkpoints):
        distance_to_cp = np.linalg.norm(position - checkpoint_position)
        max_distance = 20.0
        # v3.2: 報酬を0.7倍（時間ペナルティとバランス）
        reward += (max_distance - min(distance_to_cp, max_distance)) / max_distance * 0.7

    # 3. チェックポイント通過報酬
    if checkpoint_passed:
        reward += 200  # v3.1から維持

    # 4. ゴール到達報酬
    if goal_reached:
        reward += 500
        time_bonus = (max_steps - step_count) * 2.0
        reward += time_bonus

    # 5. 衝突ペナルティ
    if collision:
        reward -= 100

    return reward
```

### v3.0→v3.1→v3.2の変更履歴

**v3.0の問題:** 学習が不安定（Episode Reward 11~1041の激しい変動、Success Rate 0%継続）

**v3.1の変更（過剰矯正）:**
1. **時間ペナルティ強化:** `-0.5` → `-1.0`
2. **チェックポイント方向報酬抑制:** `0~1.0` → `0~0.5`
3. **チェックポイント通過報酬増加:** `+100` → `+200`

**v3.1の結果:** 学習崩壊（Episode Length 30 steps、即座に衝突）
- 時間ペナルティが強すぎて「早く死ぬ」戦略が最適に
- どこにいても時間経過でマイナス → 生存する意味がない

**v3.2の変更（バランス調整）:**
1. **時間ペナルティ緩和:** `-1.0` → `-0.7`
   - 理由: v3.1は強すぎた、v3.0とv3.1の中間値
2. **チェックポイント方向報酬増加:** `0~0.5` → `0~0.7`
   - 理由: 時間ペナルティとのバランスを取る
3. **チェックポイント通過報酬維持:** `+200`
   - 理由: v3.1の値を維持

### 各項目の詳細

#### 1. 時間ペナルティ: `-0.7 /step`
**目的:** 早くゴールするインセンティブを与える

**効果:**
- 500 stepsでゴール: -350
- 2000 stepsでゴール: -1400
- → 早い方が1050報酬高い

**理由:** 「なるべく早く」を実現するため

**バージョン履歴:**
- v3.0: `-0.5` （弱すぎ → チェックポイント近くで留まる戦略が有利）
- v3.1: `-1.0` （強すぎ → 早く死ぬ戦略が最適に）
- v3.2: `-0.7` （中間値、方向報酬とバランス）

---

#### 2. チェックポイント方向報酬: `0 ~ 0.7 /step`
**目的:** チェックポイントに近づく行動を奨励

**計算式:**
```python
reward = (max_distance - min(distance, max_distance)) / max_distance * 0.7
# max_distance = 20.0（コースサイズに応じて調整）
```

**効果:**
- チェックポイント0m: +0.7 /step
- チェックポイント10m: +0.35 /step
- チェックポイント20m以上: 0.0 /step

**時間ペナルティとのバランス:**
- チェックポイント0m: +0.7 - 0.7 = 0/step（留まってもプラマイゼロ）
- チェックポイント10m: +0.35 - 0.7 = -0.35/step（前進を促す）

**理由:**
- 観測空間にチェックポイント情報がない
- 方向報酬でチェックポイントへのガイダンスを提供
- 遠くても報酬があるため、スタート地点から学習可能

**バージョン履歴:**
- v3.0: `0~1.0` （強すぎ → 報酬変動が大きい）
- v3.1: `0~0.5` （弱すぎ → 時間ペナルティに負ける）
- v3.2: `0~0.7` （時間ペナルティ-0.7とバランス）

---

#### 3. チェックポイント通過報酬: `+200`
**目的:** チェックポイントを通過する重要性を強調

**条件:** チェックポイントを順番に通過

**理由:**
- マイルストーン報酬としてゴールへの進捗を評価
- 方向報酬だけでは不十分な場合のボーナス

**バージョン履歴:**
- v3.0: `+100` （やや弱い）
- v3.1/v3.2: `+200` （マイルストーン達成の重要性を強調）

---

#### 4. ゴール到達報酬: `+500 + time_bonus`
**目的:** 最終目標の達成を最も高く評価

**計算式:**
```python
base_reward = 500
time_bonus = (max_steps - step_count) * 2.0
total = base_reward + time_bonus
```

**効果:**
- 500 stepsでゴール: 500 + 3000 = 3500
- 1000 stepsでゴール: 500 + 2000 = 2500
- 2000 stepsでゴール: 500 + 0 = 500

**理由:**
- 早くゴールするほど高報酬
- 時間ボーナスで「なるべく早く」を強化

---

#### 5. 衝突ペナルティ: `-100`
**目的:** 壁への衝突を回避

**条件:** Box2D物理エンジンによる衝突検出

**理由:**
- 「壁にぶつからない」を実現
- エピソード終了のトリガー

---

## 削除した項目（過去バージョン）

### v1.0から削除したもの

#### 生存報酬: `+1.0 /step` ❌
**削除理由:** 時間ペナルティと矛盾
- 生存報酬: 長く走るほど高報酬
- 時間ペナルティ: 早くゴールするほど高報酬
- → 矛盾するため削除

#### 速度報酬: `+speed * 0.1` ❌
**削除理由:** 時間ペナルティで十分
- 時間ペナルティで早くゴールするインセンティブは十分
- 速度報酬は不要な複雑さ

#### 角速度ペナルティ: `-angular_velocity * 0.3` ❌
**削除理由:** 過度な制約
- カーブで曲がれなくなる
- 衝突ペナルティで十分

#### 壁接近ペナルティ: `-(0.3 - distance) * 10` ❌
**削除理由:** 衝突ペナルティで十分
- 壁に近づくこと自体は問題ではない
- 衝突しなければ良い

## 期待される学習曲線

### Phase 1: 基本走行（Iteration 1-50）
- **目標:** 衝突せずに走行
- **報酬:** -100 ~ 500
- **行動:** ランダム → 壁回避の初歩

### Phase 2: チェックポイント探索（Iteration 50-100）
- **目標:** チェックポイントに近づく
- **報酬:** 500 ~ 2000
- **行動:** 方向報酬に従ってチェックポイントへ接近

### Phase 3: チェックポイント通過（Iteration 100-200）
- **目標:** チェックポイントを通過
- **報酬:** 2000 ~ 4000
- **行動:** チェックポイント1-2個通過

### Phase 4: ゴール到達（Iteration 200-500）
- **目標:** 安定したゴール到達
- **報酬:** 4000 ~ 5000
- **行動:** 全チェックポイント通過 + ゴール
- **Success Rate:** 50% ~ 80%

## トラブルシューティング

### 学習が進まない場合

#### 症状1: Success Rate 0%が続く
**原因:** チェックポイントに到達できていない

**対策:**
1. チェックポイント方向報酬の`max_distance`を増やす（20.0 → 30.0）
2. チェックポイント通過報酬を増やす（100 → 200）

#### 症状2: 報酬が停滞
**原因:** 局所解に陥っている

**対策:**
1. Entropy係数を上げる（0.05 → 0.1）
2. Learning rateを調整（1e-4 → 3e-4）

#### 症状3: 学習が不安定
**原因:** 報酬の分散が大きい

**対策:**
1. 時間ペナルティを調整（0.5 → 0.3）
2. Batch sizeを増やす（64 → 128）

### 報酬ハッキングの検出

#### 兆候1: 高報酬だがSuccess Rate 0%
**原因:** 方向報酬だけで高報酬を得ている

**対策:**
1. 方向報酬を減らす（max: 1.0 → 0.5）
2. チェックポイント通過報酬を増やす

#### 兆候2: Episode Lengthが異常に長い
**原因:** 時間ペナルティが弱い

**対策:**
1. 時間ペナルティを増やす（0.5 → 1.0）

## Sim2Real転移の考慮事項

### 報酬関数は実機で使わない
- 実機では観測（observation）から行動（action）への推論のみ
- 報酬関数は学習時のみ使用
- → 報酬設計は実機のハードウェア制約を受けない

### 観測空間の一致が重要
- シミュレーション: [lidar, velocity, angular_velocity, last_action]
- 実機: 同じ形式で観測を取得する必要がある

### Domain Randomizationの活用
- 物理パラメータ（摩擦、質量など）をランダム化
- センサーノイズを追加
- → 実機環境の変動に対するロバスト性向上

## 評価指標

### 学習中の指標
1. **Episode Reward（平均）:** エピソード報酬の平均値
2. **Episode Length（平均）:** エピソードステップ数の平均値
3. **Success Rate:** ゴール到達率（評価時）
4. **Policy Loss:** ポリシーの損失関数
5. **Value Loss:** 価値関数の損失関数

### 評価時の指標
1. **Success Rate:** ゴール到達率（最重要）
2. **Average Time to Goal:** ゴールまでの平均時間
3. **Collision Rate:** 衝突率
4. **Checkpoint Pass Rate:** チェックポイント通過率

### 目標値
- **Success Rate > 80%** - Level 0（simple_oval）
- **Success Rate > 50%** - Level 1（実コース）
- **Average Time < 1000 steps** - 効率的な走行

## 参考文献・設計思想

### 報酬設計の原則
- **Occam's Razor:** 必要以上に複雑にしない
- **Sparse Reward with Shaping:** 基本はSparse、最小限のShaping
- **避けるべきこと:** 矛盾する報酬、過度な制約、報酬ハッキング

### 強化学習の基礎
- PPO（Proximal Policy Optimization）
- GAE（Generalized Advantage Estimation）
- Curriculum Learning
- Domain Randomization
